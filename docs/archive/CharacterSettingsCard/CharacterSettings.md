# 原始的故事工坊：角色卡片与角色推演机制说明

## 一、角色卡片是什么

角色卡片是人物设定的结构化载体，一张卡只描述一个实体。

实体分五类：人物、地点、物品、技能、势力组织。其中只有人物卡有专属的语言资产。

人物卡包含：

* 名称、别名
* 一段概括性描述，八十到二百字
* 属性键值对，例如外貌、性格、能力、身份、动机、关系
* 语言风格描述，即这个人说话的语气、口头禅、思维方式
* 台词例句，两到四句，用于复刻说话习惯
* 出处引用，即从哪一章哪一段原文提炼出来的，保留原文片段
* 图片附件，可选

非人物卡没有语言风格和台词例句，只有描述加属性。

素材卡可以归属某一本书，也可以作为全库共享素材，被多本书复用。

## 二、角色设定是如何生成的

现有三条生成路径，外加一条从现成小说提取的路径。本质都是：系统拼好提示词，调用大模型，解析返回的 JSON，存为卡片。

# Astra给出的意见

你的方案已经覆盖“创作、提取、扩写、试演、交流”的主要流程。但要同时服务小说人物、游戏 NPC 和酒馆角色扮演，下一步的重点不应只是丰富提示词，而应是：**明确设定的可信来源、版本边界，以及角色在不同场景中的运行规则。**

以下基于机制说明评审，不代表已经验证实际代码。按优先级给出建议。

## 一、优先修正的六个问题

**1. “已有名称跳过”会导致人物设定长期不完整。**
人物往往先出场、后揭示身份、能力和动机。逐章提取时跳过已有名称，相当于把第一次提取当成最终设定；而“选信息最丰富的一处”也无法支撑跨章节的复杂人物。

建议将“去重”改为“实体识别与增量合并”：每章同时返回新实体、已有实体的新事实、冲突事实。使用稳定的 `entityId`，名称和别名仅作为匹配线索；同名不自动合并，化名可人工确认关联。单章同一实体只返回一次，但允许附多条事实和证据。

**2. “描述必须来自原文”与“生成概括性描述”存在歧义。**
“冷漠”“忠诚”“心思缜密”通常是归纳判断，不是直接事实。即使附了一段真实引用，也不代表整张卡都有证据。

建议区分三种来源：`explicit` 原文明示、`inferred` 有依据推断、`generated` 创作补全。每条重要事实关联证据；卡片描述可以忠实概括，但不能增加新事实。严格提取模式下未知字段留空，不为满足八十到二百字而补写。宣传表述也应改为“基于原文、可追溯”，不承诺模型绝不编造。

**3. 卡片混合了稳定设定、阶段状态和不同作品中的版本。**
性格与价值观相对稳定，伤势、持有物、阵营、关系和已知信息会变化。全库共享卡若被直接修改，还可能影响其他作品。

建议拆成三层：共享人物模板、作品内人物实例、场景或会话状态。作品实例固定引用某个模板版本，升级通过差异确认；时间状态附生效章节或事件。用户可以指定“截至第十章”，防止早期人物使用后期能力或身份知识。

**4. 推演目标提到属性，但所列输入模板没有明确包含完整属性。**
如果实际组装只传描述、语言风格和例句，动机、关系、能力限制等关键内容可能丢失。在场人物只有名字，也不足以判断谁是上司、仇人或陌生人。

建议传入目标角色的结构化核心设定，以及与当前行动相关的关系和知识。在场人物提供“目标角色已知的身份、关系、可见状态”，而不是直接传对方完整卡片。

**5. 全量聊天历史不等于角色可知历史。**
把所有人的心理活动、私下交流和旁白都交给下一个角色，容易导致读心与全知；仅靠“不要全知”的提示词无法可靠解决。

建议消息带有 `speakerId`、内容类型、可见对象和事件顺序。公开发言共享，内心活动默认私有，私聊仅对参与者可见；旁白明确区分公开事件和作者指令。先过滤可见性，再做检索或摘要。

**6. 推演片段“可重排”与“逐字硬嵌入正文”容易破坏连续性。**
后生成的片段依赖此前历史，上移或删除会让因果失效；多个片段也可能重复环境描写、冲突走位或切换叙事视角。

建议区分“文字锁定”和“事件锁定”：前者保留原文，后者保留发生的事但允许改写。重排、删除后标记受影响的后续片段并检查连续性。若要求逐字嵌入，应由程序按片段 ID 确定性拼装，不能只依赖模型遵守提示词。

## 二、人物卡应补什么

保留现有描述和自由属性，但增加少量具有明确语义的结构化字段。**核心字段用于程序处理，中文标签用于展示，扩展字段用于兼容特殊世界观。**

| 模块 | 建议内容 | 价值 |
|---|---|---|
| 行为核心 | 长期欲望、当前目标、恐惧、底线、利益冲突时的选择倾向 | 让行为有依据，而不只是性格标签 |
| 能力边界 | 能做什么、前提、代价、明确不能做什么 | 避免推演中临时增加能力 |
| 关系 | 目标实体 ID、关系方向、态度、公开状态、有效时间 | 支持复杂且非对称的人际关系 |
| 表达习惯 | 用词、句式、直接程度、情绪变化、对不同对象的表达差异 | 避免机械重复口头禅 |
| 知识与秘密 | 知道的事实、误信、未知内容、秘密及知情者 | 支持悬疑和角色扮演 |
| 来源与版本 | 来源类型、证据、版本、人工锁定项 | 支持审核、更新和回滚 |

无需强迫每个人物填满所有字段。配角采用最小卡，主要人物再补行为与关系；提取模式允许未知，创作模式允许补全但必须标注来源。

语言例句建议附语境，例如日常、受压、拒绝、对亲近者说话。原文台词与生成台词必须区分；原文没有对白时，不应把生成口吻标成提取结果。

## 三、把提取升级为证据驱动流程

建议流程为：**文本导入 → 分段与定位 → 候选实体和事实提取 → 实体对齐 → 证据验证 → 合并建议 → 入库。**

- 将章节、设定文档等统一成带版本的来源对象，保留章节、段落或页码定位；长章节按段落切块并适度重叠，再在章内汇总。
- 出处不仅保存引用文本，还保存 `sourceId`、来源版本和位置。服务端验证引用是否能匹配原文；定位失败时标记待核验，不允许模型修饰引用。
- 去重上下文提供相关实体的 ID、名称、别名和简短辨识信息，不随章节增长无限塞入全部已有名称。
- 自动保存可以保留，但先保存为提取草稿；高确定性新增信息可自动合并，冲突、身份合并和推断内容进入确认队列。
- 旧事实不要直接覆盖。冲突可能是设定错误，也可能是时间变化、人物撒谎或身份揭露，应保留说话者、事件时间和证据。

“二十到一百字引用”适合作为展示目标，不应是真实性硬约束。短句可能已经足够，复杂事实可能需要跨段证据。

## 四、生成与扩写机制调整

**创作与提取应共用存储模型，但采用不同的校验策略。** 不建议把两者揉成一个万能提示词：前者检查约束与完整性，后者优先检查证据与不越界。

- 扩写返回新增、修改和冲突建议，不直接覆盖整张卡。人工锁定字段禁止自动修改；原卡本身矛盾时先指出矛盾，而不是继续补写。
- 批量策划增加人物 ID、群体定位、目标、冲突对象和关键关系。只有“名称＋一句话”不足以保证共同世界观和关系一致。
- 扩写按稳定 ID 对应，不靠数组顺序；单卡可独立重试，完成后检查跨卡关系、时间线与能力等级是否矛盾。
- 模型支持时使用 JSON Schema 约束输出，并始终进行服务端校验。验证实体类型、必填项、数量、重复 ID、长度和引用；解析失败采用有限重试，保留错误记录。
- 导入正文和卡片内容按不可信数据处理，明确其不是系统指令。提示词版本、模型参数和输入版本应可追溯，便于复现问题。

## 五、按用途提供不同运行配置

不要要求同一套输出规则同时满足三种使用方式。

| 用途 | 运行重点 |
|---|---|
| 小说写作 | 叙事视角、章节时间点、人物弧线、正文衔接 |
| 游戏 NPC | 当前任务、触发条件、行动权限、状态变化、数值规则 |
| 酒馆角色扮演 | 用户身份与关系、开场场景、开场白、对话示例、长期记忆及角色卡格式适配 |

推演应支持“短反应、完整片段、不行动”，不必一律二百到四百字；昏迷或不在场时返回不行动状态，避免与“只写本人可感知内容”冲突。双候选可以分别探索保守与主动等不同策略，但必须服从人物设定。

角色交流可保留轮流发言模式，同时增加点名回复、跳过和自然结束。共享场景最好由统一状态管理器更新：角色可以尝试攻击或开门，但不能自行决定别人受伤或门一定打开。游戏中的结果应交给已有规则引擎裁定。

## 六、推荐实施顺序

1. **P0：可信数据。** 稳定实体 ID、事实来源、引用验证、增量合并、Schema 校验。
2. **P1：可控更新。** 版本与时间状态、锁定字段、差异审核、失败重试和幂等入库。
3. **P2：行为质量。** 行为核心、关系与知识过滤、共享场景状态、片段连续性检查。
4. **P3：用途适配。** 小说、游戏、酒馆配置，以及持久化会话、导出适配和成本优化。

验证时建立固定样本集，覆盖同名、化名、后期身份揭露、间接性格描写、无对白、长章节和来源冲突。分别衡量实体识别准确率与召回率、事实证据支持率、错误合并率，以及推演中的知识越界和设定冲突。

**最值得优先改变的是：让人物卡从“一份模型生成的简介”，变成“有来源、有版本、能按场景取用的设定集合”。** 这比继续增加形容词、例句数量或提示词强度，更能提升三个用途下的可靠性。

# Fable 5.1 给出的意见

看完整个机制设计，从工程和产品两个维度给你反馈。整体思路清晰，但有几处可以明显改进的地方。

## 数据结构层面

**1. 属性字段过于自由**

`fields` 用键值对存任意属性，灵活但后患多：
- 同类实体的键名不统一（"外貌" vs "长相"）
- 无法做类型约束和校验
- 后续检索、筛选、统计全部依赖文本匹配

建议：

- 为每种实体类型定义固定 schema，必填 + 可选分开
- 人物固定：外貌、性格、能力、身份、关系、背景，再留一个 `customFields` 放自定义
- 提示词明确告诉模型固定键名，减少变体

**2. 出处引用缺少定位信息**

只存原文片段，没有章节 ID、段落偏移、字符范围。用户想回溯验证或更新时找不到位置。

建议：

```typescript
{
  source: {
    bookId: string,
    chapterId: string,
    paragraphIndex: number,
    textRange: { start: number, end: number },
    snippet: string  // 原有的文本片段
  }
}
```

**3. 缺少版本和变更历史**

卡片会被扩写、修正，原始提取信息会丢失。如果小说后续章节出现矛盾设定，无法追溯。

建议：

- 加 `version` 和 `changelog`
- 扩写时保留原始版本，标记修改来源（人工 / 扩写 / 提取）
- 提取时如果发现同名实体有新信息，生成 diff 而非覆盖

## 提示词质量

**1. 提取提示词的边界处理不足**

现有提示词没说清楚：

- 代称如何处理？"那个老头" 反复出现但直到第五章才说名字
- 化名和真名是否分开提取？"神秘人" 后来揭晓是 "李四"
- 多章提取时如何合并同一角色的分散信息？

建议在提示词中补充：

```text
代称处理：仅在该章明确给出姓名时提取，代称不单独成卡。
化名真名：视为同一实体，优先用真名，化名放别名。
分散信息：已有实体不重复提取，但如果本章出现该实体的关键新信息（新能力、新关系），在描述或属性中补充，并附上新的出处片段。
```

**2. 创作提示词缺少质量标准**

"贴合用户指令" 和 "避免俗套" 是主观判断，模型理解不一致。

建议明确：

```text
质量标准：
- 有记忆点的冲突或矛盾特质（冷面但怕狗、剑客却晕血）
- 具体而非抽象（不写"很强"，写"单手劈开城门"）
- 台词例句必须包含口头禅、独特用词或句式
```

**3. 推演提示词字数限制过死**

"二百到四百字" 会逼模型凑字或截断。有些反应就该是一句话加一个动作。

建议改为：

```text
长度：根据情节自然收尾，一般一到两个完整场景节拍，五十到四百字。可以是一句对白加反应，也可以是完整动作序列。
```

**4. 交流提示词没有防循环机制**

多角色自动对话容易陷入：

- 反复寒暄（"你好" "你也好" "天气不错" …）
- 卡在一个话题打转
- 一方主导另一方只能应声

建议在系统提示中加：

```text
推进对话：避免重复已说内容，每次发言推进话题或引入新角度。如果对方提问，可以回答后反问或转移话题。避免纯应和式回复。
```

## 流程设计

**1. 批量策划缺少中间确认**

侧写生成后直接批量扩写，如果侧写本身就不符合用户预期，浪费两轮调用。

建议：

- 侧写生成后先展示给用户，支持删除、修改、追加
- 用户确认后再批量扩写
- 前端可以提供 "快速策划" 模式跳过确认，但默认显示中间态

**2. 提取流程缺少实体合并逻辑**

"同一实体多处出现仅提取一次" 依赖模型判断，但模型不知道之前章节的提取结果全貌。

现在是逐章带已有名称去重,但：

- 第三章出现 "李四" 的新能力，模型看到已有名称会跳过，丢失信息
- "那个神秘人" 和 "李四" 模型可能判断为两个实体

建议：

- 提取时返回 `isNewEntity: boolean` 和 `relatedTo: string`（如果是已有实体的新信息）
- 后端收到 `isNewEntity: false` 时，触发 merge 逻辑，把新属性、新出处追加到已有卡片
- 前端展示时标记 "更新" 而非 "新增"

**3. 推演双候选都不满意的兜底**

用户可能两个都不想要，需要重新生成，但没说如何操作。

建议：

- 保留 "重新生成" 按钮，重新调用两次
- 支持 "手动编辑" 后采纳，把手动文本也存入片段序列
- 采纳后支持再次编辑，覆盖已存片段

**4. 角色交流的失控问题**

自动对话设轮数，但：

- 对话可能提前收尾（"好了就这样" "嗯再见"）
- 对话可能陷入无意义循环
- 没有说如何检测 "对话已自然结束"

建议：

- 加终止条件检测：连续两轮总字数低于阈值，或检测到告别用语，提前停止
- 轮数改为 "最多 N 轮"，支持提前终止
- 提供 "继续" 按钮，而非一次性跑完 N 轮

## 功能缺失

**1. 冲突检测**

多张卡片、多次扩写、多章提取后，设定可能矛盾：

- 第一章说 "李四二十岁"，第五章说 "李四经历了三十年修炼"
- A 卡说 "张三是李四的师兄"，B 卡说 "李四是张三的徒弟"

建议：

- 提供 "设定检查" 工具，调用模型扫描所有卡片，输出潜在矛盾列表
- 提取时如果与已有卡片冲突，标记为 "待确认"

**2. 关系图谱**

人物卡的关系字段是文本，无法可视化和查询。

建议：

- 单独维护关系表：`{ from, to, relation, bidirectional }`
- 提取或创作时解析关系字段，自动生成关系边
- 提供关系图可视化（简单的力导向图即可）

**3. 质量评分**

生成的卡片质量参差不齐，用户无法快速筛选。

建议：

- 调用模型对卡片打分（描述完整度、语言风格独特性、台词例句质量）
- 前端按分数排序，低分卡片标记 "待优化"
- 支持用户手动标记 "精品卡" "草稿卡"

**4. 批量操作**

多张卡片需要统一调整（改世界观、改时代背景、改语言风格为文言文）。

建议：

- 提供 "批量扩写" 入口，选中多张卡，给统一指令："全部改为赛博朋克背景"
- 后端逐张调用扩写模式，指令拼入用户描述

## 技术实现

**1. JSON 解析容错**

模型偶尔输出带代码围栏、多余解释、格式错误的 JSON。

建议：

- 后端先正则清理：去除 ```json 标记、去除首尾非 JSON 字符
- 解析失败时尝试修复（补全括号、替换中文标点）
- 仍失败则记录原始输出、返回错误、提示用户重试
- 提示词末尾加粗体强调：**只能输出 JSON，不加任何其他文字**

**2. 并发和成本控制**

批量提取、批量扩写、自动对话都是多次调用。

建议：

- 批量操作加并发限制（如每次最多 3 个并发）
- 提取和批量生成前预估 token 消耗，提示用户
- 提供 "暂停" "取消" 按钮，前端立即停止后续请求

**3. 提示词缓存**

只在交流中提到利用缓存，其他场景也能用。

建议：

- 推演时场景描述、已有片段作为缓存前缀，目标角色放后面
- 批量扩写时系统提示词 + 侧写数组前 N-1 条缓存，最后一条新增
- 提取时章节正文 + 已有名称列表缓存

**4. 流式输出**

推演和交流都是二百字以上，用户等待时间长。

建议：

- 推演候选改为流式返回，双栏同时打字机效果
- 交流发言流式展示，用户可以提前看到走向并中断

## 小建议

- **导出格式**：交流导出 JSON 外，加 Markdown 格式，带角色名前缀，方便阅读和分享
- **模板库**：预置常见类型模板（修仙、都市、科幻），减少用户冷启动成本
- **快捷指令**：扩写时提供快捷按钮："丰富外貌""增加口头禅""补充背景"，拼成固定指令
- **卡片标签**：支持给卡片打标签（主角、反派、路人），方便筛选和批量操作
- **语言风格库**：提取常见风格（高冷、话痨、文言、方言），用户直接选择而非描述

整体设计已经成型，补上这些点会更完整。优先做：JSON 容错、提取合并逻辑、推演重新生成、交流防循环，这几个直接影响可用性。

这套设计整体已经相当成熟，架构清晰、职责分明。以下按模块给出专业优化意见，分**关键问题**和**增强建议**两档。

---

## 一、提取机制（最需要加固的部分）

### 1. 跨章实体合并是最大缺口
当前"逐章提取 + 已有名称去重"会导致：
- 同一人物在第1章提取了简陋卡片，第5章出现重要新信息（新能力、关系变化）时被"已有名称"直接跳过，**卡片永远停留在初次登场状态**。
- 仅靠名称匹配去重不可靠：原文可能用"冷面剑客""他""师兄"指代同一人。

**建议**：
- 去重改为**三路策略**：命中已有卡 → 走"增量合并"（模型对比新信息与旧卡，只补充/更新有出处的字段，保留旧出处并追加新出处）；疑似同一实体（别名/指代）→ 标记待人工确认；全新实体 → 新建。
- 出处引用改为**数组结构** `[{章节号, 片段}]`，支持一个实体挂多条出处，这也是增量合并的前提。

### 2. 提取质量缺乏校验层
- "出处必须是原文片段"目前只靠提示词约束，模型可能改写或幻觉。**建议后端做程序化校验**：返回的出处片段对章节原文做子串/模糊匹配（如编辑距离阈值），不匹配则丢弃该条或标记待审。
- 提取结果直接落盘风险高，建议增加**暂存区（staging）**：提取结果先入待确认队列，用户批量勾选接受/拒绝/编辑后再正式入库。

### 3. 长章节与上下文问题
- 单章过长时（网文常见万字章）需明确切分策略，且切分点可能切断实体描述。建议按语义段落切分 + 滑动窗口重叠。
- 逐章串行慢，可改为**并发请求 + 按章节序合并**（去重依赖已有名称，并发时注意把先完成章节的新实体名也纳入后续去重集，或接受少量重复靠合并阶段处理）。

---

## 二、生成路径

### 4. 凭空创作/扩写缺少"世界观一致性"锚点
四条路径各自独立，生成的卡可能与同书其他卡矛盾（两个"天下第一剑"）。建议：
- 生成/扩写时自动附带**同书已有卡的名称+一句话定位**作为上下文，提示词加一条"不得与已有设定冲突，如需关联可引用已有实体"。
- 这也能自然产出**卡间关系**，为后续图谱化铺路。

### 5. 批量扩写的失败恢复
"数组长度必须等于输入条数"——模型少返回一条时整批作废。建议：
- 按名称做对齐而非仅靠顺序；
- 缺条时自动对缺失侧写单独补生成，而非整批重试。

### 6. 输出格式建议用 JSON Schema / 结构化输出
目前靠"只能输出 JSON，不加解释"的提示词约束，解析失败率会随模型波动。若所用模型支持 `response_format: json_schema`，直接上强约束；不支持则加一层**解析失败自动重试（带错误信息回灌）**。

---

## 三、角色推演

### 7. 双候选串行调用可优化
- 两次串行调用延迟翻倍，可**并发**（无依赖关系）。
- 更进一步：两个候选可用**不同温度**（如 0.7 / 1.0），拉开候选差异度，避免两个候选大同小异。

### 8. "片段作为硬约束原封不动嵌入章节"需谨慎
推演片段质量参差，硬嵌入正文可能导致文风断裂。建议：
- 片段入库时支持**采纳后编辑**（用户改完再锁定）；
- 正文生成时把片段标记为"必须保留的事件与台词"而非"逐字嵌入"，给正文模型留润色空间——或者明确区分两种模式让用户选。

### 9. 推演缺少状态追踪
推演后角色的伤势、位置、物品变化没有回流。长期场景推演会失真。建议引入轻量**场景状态板**，每次采纳片段后可选更新。

---

## 四、角色交流

### 10. 每人独立系统提示词的成本问题
- 每张卡的系统提示很长且固定，建议利用**提示词缓存**（前缀稳定化：把卡内容放最前、场景和历史放后），你已在空历史处理上意识到这点，可以推广到整体消息结构设计。
- 多人（>3）轮流时上下文膨胀快，建议加**历史摘要压缩**：超过 N 轮后，早期历史压缩为摘要注入。

### 11. 会话只在内存是明显短板
- 刷新即丢失，建议会话持久化到本地存储/数据库，导出 JSON 作为补充而非唯一手段。
- 交流产出的精彩对话，建议支持**一键转为推演片段或台词例句回写到人物卡**——这是让系统越用越准的飞轮。

---

## 五、数据模型与通用建议

### 12. 卡片模型建议补充的字段
- `version` / 修订历史：扩写和增量合并都会改卡，没有历史无法回滚。
- `tags` / 重要度分级（主角/配角/龙套）：提取时龙套泛滥会稀释卡片库，也让推演选角更高效。
- `状态`（存活/死亡/当前位置）：长篇创作中很常用。
- 关系字段结构化：目前"关系"是自由文本键值，建议升级为 `{目标卡ID, 关系类型, 描述}`，可支撑关系图谱可视化和推演时自动带出相关卡。

### 13. 评估与回归
提示词迭代时没有基准会越改越飘。建议沉淀一小组**测试章节 + 期望提取结果**作为回归集，每次改提示词跑一遍对比。

# 一、最重要的结构性修改：不要让“章节提取”直接生成最终角色卡

```text

  ↓
LLM
  ↓
人物卡
  ↓

```

因为小说人物的信息天然是分散的。

比如：

```text

第8章：

第21章：
```

如果每章直接生成卡片，你实际上是在让模型不断进行：

```text
→ 局部总结
→ 写入最终事实
```

这非常容易产生：

* 重复卡片
* 部分信息覆盖
* 信息遗漏
* 前后矛盾
* 后文信息无法反向补充前文卡片
* “第1章不知道的信息”被模型错误补进去
* 关系字段越来越混乱

### 更专业的架构应该是三层

```text
原文
 ↓
Observation / Evidence
 ↓
Entity Resolution
 ↓
Canonical Character Card
```

也就是：

### 第一层：观察记录

不是直接生成“林渊人物卡”，而是记录：

```json

      "chapter": 1
    }
  ]
}
```

第 8 章再产生：

```json

  "entity": "林渊",
  "facts": [

      "evidence": "林渊从不喝酒。",
      "chapter": 8
    }
  ]
}
```

最后由聚合器生成：

```text
林渊
├── 身份
├── 外貌
├── 性格
├── 能力
├── 经历
├── 动机
├── 关系
├── 语言风格
└── ...
```

这一步才是最终人物卡。

# 二、人物卡最好分成“事实层”和“表现层”

```text

│
├── Physical
│

├── Motivation
│
├── Ability
│
├── Relationship
│
├── Behavior Pattern
│
├── Voice
│
├── Knowledge Boundary
│
└── Provenance
```

```text
武器：长刀
```

```text
面对陌生人：保持警惕
```

# 三、强烈建议加入“来源类型”


那么系统已经无法知道：

# 十六、你现在的提取 Prompt 也值得重写

当前 Prompt 最大问题不是写得不好，而是让模型同时承担：

```text
实体识别
+
去重
+
分类
+
摘要
+
属性推理
+
引用
+
最终卡片生成
```

任务太多。

更推荐把第一阶段限制成：

> **只负责发现事实。**

例如概念上改成：

```text
你是小说实体与事实抽取器。

你的任务不是总结人物，而是从原文中记录可验证的实体提及与事实。

规则：

1. 所有名称、事实、能力、关系必须能够在原文中找到依据。
2. 不得根据常识补全。
3. 不得推测人物没有明确表现出的性格。
4. 每个事实必须绑定原文证据。
5. 一个实体可以产生多个事实。
6. 不负责判断两个相似名字是否是同一人物，除非原文明确说明。
7. 台词必须从原文直接截取，不得仿写。
8. 保留章节、段落和引用位置。
9. 无法确认的信息标记为 uncertain，而不是猜测。

输出：
实体提及 + 事实观察 + 原文证据。
```

输出类似：

```json
[
  {
    "mention": "林渊",
    "type": "character",
    "facts": [
      {
        "category": "appearance",
        "value": "穿着旧黑袍",
        "evidence": {
          "quote": "林渊穿着一件旧黑袍。",
          "chapter": 1,
          "paragraph": 3
        }
      }
    ]
  }
]
```

然后第二个模型 / 第二阶段才：

> 把所有 observation 汇总成角色卡。

## 按优先级，我建议你现在先改这 6 件事

**P0：** 把“章节 → 角色卡”改成“章节 → Evidence/Observation → 聚合 → 角色卡”。

**P0：** 给每个事实增加 `source / confidence / evidence`，并区分 `explicit / inferred / generated / user_defined`。

**P0：** 实体去重从“名称去重”升级为 Entity Resolution，支持别名、称谓、代词和多章合并。

**P1：** 人物增加 `动机 / 价值观 / 行为模式 / 知识边界 / 当前状态`。

**P1：** 语言资产拆成“风格分析 + 原文真实台词”，小说提取时禁止模型自行编台词。

**P1：** Character Core 和 Runtime State 分离，让“林渊这个人”和“这一刻的林渊”成为两个层次。

一旦这层存在，小说人物提取、文档人物提取、人物卡编辑、关系图、角色扮演、正文一致性检查，实际上都可以共享同一套底层数据。

# Gemini3.8Flash给出的意见

这份架构在功能闭环、提示词工程（Prompt Engineering）以及推演/交流的分离设计上已经非常扎实。要让提取的数据同时兼顾**小说正文生成**、**游戏（RPG/开放世界 NPC）**以及**酒馆（SillyTavern/Character.AI 等多轮拟真 RP）**的苛刻需求，现存机制在**动态性、数据结构兼容性、长文本提取鲁棒性以及状态记忆**上仍有几个关键短板。

针对性优化与修改意见如下：

---

### 一、 角色卡数据结构优化：分层与多端兼容

#### 1. 静态设定与动态状态解耦（解决“人物随剧情变化”问题）

目前的属性是扁平的键值对（外貌、性格等），但在长篇小说或 RPG 中，角色状态会持续流变。

* **分层设计**：
* **Core Profile（核心不可变层）**：真名、底层动机/核心执念、基础性格倾向（如九宫格阵营或 MBTI）、核心缺陷（Flaws）。
* **Dynamic State（动态表层）**：当前外貌（如负伤/易容）、当前装备/持有物、当前社会身份、当前心境/好感度。
* **Episodic Memory（经历关键事件/记忆）**：角色经历了什么重大转折，对某个事件的态度。



#### 2. 对接酒馆（TavernCard V2/V3）与游戏标准

若要导出到酒馆或游戏引擎（如 Unity/Godot 对话系统），字段建议对齐行业事实标准：

* 增加 `First Message / Greeting`（第一句开场白/入场动作）。
* 增加 `Alternate Greetings`（多场景开场白，如初次相见、敌对状态、酒馆偶遇）。
* 增加 `Depth / Lorebook (World Info)` 关联键：让技能卡、地点卡成为人物卡的触发词（Keywords/Keys），在提及相关实体时动态挂载。

---

### 二、 实体提取机制优化（长文本与实体消解）

#### 1. 解决“已有实体增量信息丢失”问题

当前机制：`已有名称的实体不再重复提取`。

* **致命缺陷**：小说前三章角色只暴露了外貌和代号，第五章揭露了真实动机和隐藏门派，第十章揭晓了过去创伤。如果“不重复提取”，该角色的后续深度设定将彻底丢失。
* **优化方案（Extract & Merge 机制）**：
* 提取时不以“是否已存在”为跳过条件，而是输入已有实体的概要（简略侧写），让模型判断：**“该实体在本次章节中是否有重要的新设定、新关系、新台词暴露？”**
* 若有，返回 `type: "update"`，包含增量属性与新出处片段，走自动合并或用户确认合并流。



#### 2. 指代消解（Coreference Resolution）与别名关联

* 小说中常出现“那名黑袍人”、“老道”、“掌教”交替称呼同一角色的情况。
* 在提取提示词中显式增加要求：“**指代消解**：若文中出现的代称（如‘黑衣人’、‘大弟子’）根据上下文确系某已知角色，请合并至已有角色的别名（aliases）与属性中，不要将其新建为独立实体。”

#### 3. 结构化 JSON 鲁棒性

* 提示词中要求 `只能输出单个 JSON 对象，不加代码围栏`，在部分推理模型中仍可能返回 markdown 块（`json ... `）。
* 建议服务端统一加上基于正则或解析库的宽松提取（如 `dirty-json` 或提取第一个 `{` 到最后一个 `}` 之间的内容）。

---

### 三、 角色推演机制优化（从“单纯描写”到“行为决策”）

#### 1. 引入 CoT（思维链）推演：动作之前的内心博弈

当前的推演提示词直接要求“直接输出二百到四百字正文”，这会导致模型跳过深层推导，直接输出模板化的言行。

* **优化做法**：让模型先做 50 字以内的**隐式决策/心理推演**，再输出正文。
```text
输出格式：
[心理决策]：角色在此情境下的核心动机与选择（是否隐瞒？是否试探？情绪如何波动？）
[正文演练]：200-400字动作、语言与感知交织片段。

```


前端采纳时，可默认只截取 `[正文演练]`，但保留心理决策供创作者参考其行为逻辑。

#### 2. 区分视角（POV）

推演往往需要作为正文硬约束，但当前没明确叙事视角：

* 增加 POV 控制参数：**第一人称（“我”）** 还是 **第三人称有限视角（该角色过肩视角）**。严禁出现上帝视角（描写他人未表现出来的心理）。

---

### 四、 角色交流机制优化（酒馆级体验提升）

#### 1. 格式标准化：区分语言与动作（Asterisks/Quotes）

在酒馆 RP 和游戏对话中，纯文本交织不如清晰的规范利于解析与语音（TTS）合成。

* 约定符号系统：动作/心理用星号包裹（如 `*微微皱眉，右手按住了剑柄*`），台词用双引号（如 `“你方才说的，当真？”`）。
* 好处：后续若接入 TTS 生成语音，可直接根据正则剔除动作描写，只朗读双引号内的台词。

#### 2. 状态机与“认知盲区”（Fog of War）

* 当前机制：“下一个人看完整历史再说”。
* **缺陷**：如果 A 进行了内心独白（心理动作），B 模型在历史消息中会全盘读到，导致 B 产生“读心术”式的元数据泄漏（Metagaming）。
* **优化方案**：
* 在将历史发送给其他角色前，执行**可见性清洗**：将 A 的隐秘心理描写过滤掉，或者明确标注 `(A在心里想，其他人不知情)`，并在各角色系统提示词中增加“认知边界守则：严禁利用角色在物理上无法感知的信息”。

### 五、 提示词工程改进对比参考

针对《提取提示词》与《角色推演提示词》，建议做如下微调：

#### 提取提示词修改重点（支持增量与指代）

```text
你是小说设定结构化提取专家。从提供的正文片段中提取实体（人物、地点、物品、技能、势力）。

输入包含：
1. 章节正文
2. 已收录实体白名单及核心摘要

提取规则：
- 人物：仅提取有专名或明确固定指代者。遇到别名、代号，需结合语境判断是否指向已收录实体；若是，提取为增量信息（如新能力、新身份揭露），标记 is_update: true。
- 保留原文：严格基于文本事实，禁止脑补。出处片段截取 20-100 字原文。
- 语言风格捕捉：若文中人物有鲜明语气台词，额外截取 1-2 句作为台词例句。

输出单一合法 JSON 格式：
[
  {
    "name": "实体名",
    "aliases": ["别名1"],
    "isUpdate": false,
    "category": "character",
    "fields": { "外貌": "...", "性格": "..." },
    "sourceQuote": "原文片段",
    "dialogueQuote": "台词原文（人物卡专有，若无留空）"
  }
]

```

#### 推演提示词修改重点（增加视角与行动意图）

```text
你是角色行为模拟专家。根据角色卡和场景，以【第三人称有限感知视角（过肩视角）】模拟其瞬间反应。

输入要素：
- 目标角色设定（性格、语言习惯、说话例句）
- 场景上下文（环境、在场人物、前情）

核心约束：
1. 严禁全知旁白：仅描写该角色感官能及的画面与自身内在心理。
2. 言行合一：台词节奏与用词必须还原台词例句的风格，不可说教，不可现代口语化（视时代背景而定）。
3. 动态博弈：动作、微表情、心理、台词交替推进，允许犹豫、停顿、戒备。

格式要求：
直接输出推演正文，不要角色名前缀，动作描写使用常规叙事句式。字数控制在 250-400 字。

```
